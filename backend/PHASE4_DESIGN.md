# Phase 4 Design — Fixed-Price Purchases, Reservations, Payments, Refunds and Delivery

**Task:** P4-D1, design only
**Baseline:** `5688383` (`docs: close Phase 3 gate`)
**Scope:** backend design; no code, migration, schema, specification, or security-checklist changes are part of this task.

The decisions in `DECISIONS_2026-10-25.md` Q1–Q19 and its addendum, and the Phase 4 requirements in `specs.md`, are the settled product inputs for this design. This document does not edit or supersede those files. In particular:

- **D1 = A — owner-confirmed in chat 2026-10-29:** Phase 4 accepts buyer payments only. Seller payouts remain manual under FR-65; gateway payout automation is out of scope.
- **D2 = A — owner-confirmed in chat 2026-10-29:** a real second Admin has their own authenticator; provide a command to create Admins. `PAYMENTS_ENABLED` must remain blocked unless two distinct Admin accounts have enrolled authenticators.
- **O1 — owner-confirmed in chat 2026-10-29:** a payment confirmed after its reservation has expired is always refunded through the system path; the reservation is never reopened.
- **O2 — owner-confirmed in chat 2026-10-29:** only an Admin may mark handover to courier, only after courier pickup is confirmed, and only with a required confirmation reference/comment note. Sellers cannot mark handover. This transition ends pre-handover buyer cancellation and stops the 72-hour clock.
- **O3 — owner-confirmed in chat 2026-10-29:** the seller handover deadline is exactly 72 hours from funding, measured from `funded_at` using database time; there is no calendar-day or business-day interpretation.
- **O4 — owner-confirmed in chat 2026-10-29:** if Admin records a pickup that occurred before the 72-hour deadline after the system has already auto-cancelled the order and issued a refund, the order is not reopened. Staff record the exception, arrange delivery or return manually from the admin panel, and handle any further refund through the manual two-Admin path. The admin panel displays the server-calculated refundable amount securely.

No live gateway is selected, no legal clearance is implied, and payment collection remains disabled until the separate launch gate passes.

## 1. Current-state summary and legacy conflicts

### a. Orders and COD columns

The current `orders` table has `accepted_offer_id UUID NOT NULL REFERENCES offers(id)`, `agreed_item_price`, `delivery_fee`, generated `total_cod_amount`, required `delivery_address`, required `payment_method_preference`, and `status` defaulting to `bag`; the `order_status` enum includes `bag`, `order_placed`, fulfillment/hold/completion states, `cancelled`, `refused_at_door`, `return_requested`, and `returned` (`db/migrations/001_initial_schema.sql:230-256`). This is incompatible with fixed-price Buy unless `accepted_offer_id` becomes nullable and the new purchase path does not require an offer.

- `orders.service.js` creates offer-backed Bag rows (`src/modules/orders.service.js:72-85`), checks/updates a Bag during COD checkout (`:89-121`), and changes order status or cancels an order (`:129-173`). Its reservation query treats selected order statuses as a reservation (`:30-45`). `orders.routes.js` exposes the authenticated legacy checkout, cancel, and history paths (`src/routes/orders.routes.js:6-19`).
- COD total reads are routed through `orders.getCodAmountDue()` (`src/modules/orders.service.js:224-228`); `payments.service.js` reads it and records `cod_collections`, then changes the order to `held` and starts a payout hold (`src/modules/payments.service.js:24-53`). `payout.service.js` gets the item price through that same read and changes completed order state during release (`src/modules/payout.service.js:68-85`). `settlement.service.js` looks up the order’s seller (`src/modules/settlement.service.js:99-104`).
- For new fixed-price orders, the legacy payout read remains compatible because `payout.service.releasePayout()` takes `agreed_item_price` from `getCodAmountDue()` (`src/modules/payout.service.js:70-71`), then passes it to `settlement.service.calculateSettlement()` (`src/modules/settlement.service.js:63`), which calculates commission from that item price (`src/modules/settlement.service.js:76`). `getCodAmountDue()` selects `total_cod_amount` as well as `agreed_item_price` and `delivery_fee` (`src/modules/orders.service.js:225-226`); the generated `total_cod_amount` remains a legacy COD value only and no new-flow code may read it as a payment amount.

## 2. Data model — expand-only

### Options and recommendation

**A. Separate `reservations` table (recommended).** A reservation is an explicit, time-bounded allocation with its own status, timestamps, buyer, listing and locked checkout snapshot. Add `orders.reservation_id` as unique nullable FK during expansion, and create the order and reservation in one Buy transaction. The reservation row and a partial unique index on active listing reservations make the core allocation invariant explicit. Order status remains the lifecycle/read-model field for existing order consumers; reservation and order changes commit together. Keep the reservation row after expiry/cancellation for audit and test history.

**B. Reservation as an `orders.status` only.** Extend the existing enum with `reserved` and add a partial unique index over listing IDs where an order has a reservation-active status. This avoids an additional reservation aggregate, but couples reservation expiry and allocation to an order table whose current required `accepted_offer_id`, COD fields, history, and many legacy consumers are already in transition. Partial unique indexes also require every active→inactive path to update order status correctly. This is feasible but less isolated.

Choose A to keep the new reservation lifecycle explicit and auditable. Avoid maintaining two independently writable truths: write `reservations.status` and the order’s corresponding public lifecycle status in the same transaction, and derive reservation availability only from the canonical reservation row after migration.

**Enum migration transaction constraint:** `db/migrate.js` configures `node-pg-migrate` with `singleTransaction: true`, which wraps all pending migrations in one transaction. The new order-status labels may be added in the single Phase 4 schema migration run, but no SQL in that run may reference those labels. Later migration runs and application code may use them after the migration transaction commits.

### Order lifecycle status storage (Q19b)

Two approaches preserve `reserved` as the canonical reservation status required by Q19b:

- **A. Add `reserved`, `payment_pending`, and `funded` to `order_status`.** New-flow `orders.status` uses `reserved` as the canonical state; `bag` remains only a temporary compatibility alias at read/API boundaries for old data. This keeps one order lifecycle status for both existing consumers and the new flow. The labels are added in the single Phase 4 migration run, and no SQL in that run may reference them; they are usable by later migration runs or application code after commit. The general integration setup (`test/integration/global-setup.js`) loads `schema.sql` directly, so migration integration tests must also exercise the migration runner.
- **B. Add a constrained lifecycle column for the new flow without altering `order_status`.** A new column such as `lifecycle_status` carries `reserved` as the canonical state for fixed-price orders and is constrained to its allowed new-flow values; existing `status` and enum values remain for legacy orders. Q19b is met by making the new column authoritative for new-flow order state and mapping it to the external/API `reserved` value, with no second writable canonical state. This avoids PostgreSQL's enum commit boundary, but requires every new-flow reader, writer, and API projection to use the new column while legacy consumers continue to use `status`.

**Stage 2 default recommendation, not an owner decision: A.** Prefer one canonical order-status field and avoid a second lifecycle column with parallel legacy/new-flow readers. The required separate migration run and matching migration test are operational constraints, not reasons to use a permanently split lifecycle model. The owner retains the decision.

### Expand-only schema inventory

Implement as prose/schema plan only; exact SQL, migration numbering and ownership are for the implementation stages.

- **`reservations`**: `id`, `listing_id`, `buyer_id`, `seller_id`, `status` (`active`, `paid`, `expired`, `cancelled`, `released`), `item_price_snapshot NUMERIC(12,2)`, `delivery_fee_snapshot NUMERIC(12,2)`, `total_amount_snapshot NUMERIC(12,2)`, `currency`, `address_snapshot` (structured JSONB or normalized immutable recipient/address columns), `created_at`, `expires_at`, `paid_at`, `ended_at`, `end_reason`, timestamps. Require positive item price, nonnegative fee, total equal to item plus fee, supported currency, valid status, and a complete address snapshot. Add a partial unique index on `listing_id WHERE status = 'active'`. Keep expiry decisions based on database time; the worker transitions expired rows out of `active`.
- **`orders` additive changes**: alter `accepted_offer_id` to nullable; add unique nullable `reservation_id`; add `reserved`, `payment_pending`, and `funded` to the order-status enum if Option A is selected (or use the constrained lifecycle column in Option B); and add `funded_at`, `handover_deadline_at`, and `handed_over_at`. In the Buy transaction, write `agreed_item_price` and `delivery_fee` from the immutable reservation snapshot; a database `CHECK` or trigger must guarantee that both order values equal their reservation snapshot values. Do not use money placeholders. Until later additive NOT NULL relaxation, only `delivery_address = '[reservation snapshot]'` and `payment_method_preference = 'fixed_price_gateway'` may hold placeholders. The canonical immutable amount/currency/address snapshot lives on `reservations`, linked by `reservation_id`; the matching order money values are protected copies, not independently mutable amounts. Keep `total_cod_amount` generated and never write it directly; no new-flow code may read it as a payment amount. Additive relaxation of legacy NOT NULL constraints remains expand-only and must preserve legacy COD behavior. Any legacy COD checkout, COD collection, or payout-hold-on-COD path must refuse an order with a non-NULL `reservation_id`.
- **`payments`**: `id`, `order_id`, `provider`, provider payment/reference IDs, `status` (`created`, `pending`, `succeeded`, `failed`, `cancelled`, `late`, `refunded/partially_refunded` as a derived or carefully maintained projection), amount and actual gateway fee as `NUMERIC(12,2)` with currency snapshots, unique application idempotency key, hosted checkout reference/URL as needed, provider timestamps, created/updated timestamps. Unique provider reference where present; permit multiple failed attempts but at most one accepted successful capture per order. Never use JavaScript floats for money.
- **`refunds`**: `id`, `payment_id`, `order_id`, `trigger` (`system_cancel`, `system_expiry`, `system_handover_timeout`, `manual_admin`), positive `amount NUMERIC(12,2)` with currency, `status` (`requested`, `approved`, `pending`, `succeeded`, `failed`, `reversed`), gateway refund reference, globally unique idempotency key, `requested_by`, `approved_by`, request/approval/completion timestamps, reason/decision note, and audit timestamps. Require manual requester and approver to differ; system-triggered rows use a distinct authorization path. Row-level `CHECK` constraints validate positive amounts and valid requester/approver shape. Aggregate invariant: total succeeded plus reserved/in-flight refunds must not exceed the captured refundable amount (captured total less prior refunds). A normal SQL `CHECK` cannot safely aggregate other rows; enforce the aggregate under a locked payment row in one transaction and, if database-enforced defense-in-depth is chosen, a trigger/constraint-trigger with the same serialization rule. Partial-refund data and validation only—do not expose a partial-refund workflow.
- **Append-only `ledger_entries`**: payment capture, gateway fee, refund and reversing/correction entries, with order/payment/refund references, currency, signed `NUMERIC(12,2)` amount, entry type, unique source/idempotency key and timestamps. Database triggers reject `UPDATE` and `DELETE` on ledger and audit tables; role separation is additional defense only. Corrections are compensating entries, not updates/deletes.
- **`webhook_inbox`**: provider, unique provider event ID, event type, raw body bytes, signature/timestamp metadata, verified receipt time, processing state, attempts/error code, linked payment, received/processed timestamps. `UNIQUE(provider, provider_event_id)`. Store only after successful signature verification; restrict raw payload retention/access and never log it.
- **Append-only `money_audit_events`** (or a shared append-only audit table): actor, action, order/payment/refund IDs, request/decision metadata, requester/approver identity, reason, request correlation ID and timestamps. Database triggers reject `UPDATE` and `DELETE` here too; role separation remains supplemental. Never store TOTP codes, secrets, full credentials, or raw provider secrets.
- **Settings and coverage**: add validated scalar settings for reservation minutes, maximum unpaid reservations, delivery fee in PKR (`NUMERIC(12,2)`), and handover deadline hours (72). Add a supported-delivery-city relation referencing `cities`; keep unsupported or inactive cities out of Buy.
- **Existing COD columns and tables**: left intact and untouched by the new buyer-payment logic throughout all expand stages. Any later removal is a separately approved contract step.

## 3. State machine

### Listing availability

- `draft`/`pending_review` → `published`: existing moderation approval.
- `listing_status` has no `reserved` or `sold` values. A listing remains `published` while available, reserved, or sold; availability is derived from reservation/order rows and never written as a listing status.
- **Reserved** means a linked reservation is `active` and `expires_at > database time`. Buy creates that state atomically and a second active reservation for the listing is refused.
- **Sold** means the linked reservation is `paid` and its order is in a funded-or-later state other than `cancelled`; this remains sold through delivery, the complaint/hold window, and completion. A late capture after expiration is refunded and does not mark the reservation paid or the listing sold. An expired or cancelled unpaid reservation is available again only while `listing_status = 'published'`; a funded order cancelled with a full refund is no longer sold, but its terminal reservation is never reopened.
- Discovery derives the live `reserved` badge from the active, unexpired reservation predicate and excludes listings satisfying the sold predicate. The `listing_search` projection derives `is_reserved` and `is_sold` from those same reservation/order predicates; search excludes `is_sold` and badges `is_reserved`. No derived availability changes `listing_status`.
- `published` listings may become `paused`, `removed`, or `unpublished` through existing seller/Admin paths, except seller pause/removal while a reservation is active is blocked; Admin take-down is allowed and triggers the documented release/refund path.
- A pending price revision cannot be approved while the listing has an active reservation. It remains pending after expiry/cancellation and requires normal review; notify the seller in-dashboard and in-app.

### Reservation

- `active` → `paid`: verified webhook wins the serialized expiry/payment race while the reservation is still valid.
- `active` → `expired`: expiry worker or a database-time check in Buy/payment processing finds expiry reached and atomically releases the listing.
- `active` → `cancelled`: buyer cancellation before courier handover, subject to the order/payment state; a captured payment creates a system full-refund intent in the same transaction.
- `active` → `released`: authorized Admin take-down/other permitted release path with the corresponding reason and refund intent where captured.
- Terminal reservation states do not return to `active`. A provider event for an ended reservation never reopens it; a verified late capture is recorded and routed to an idempotent system refund.

### Order and payment

- Order: `reserved` → `payment_pending` → `funded` → `seller_preparing` → `handed_to_delivery` → `out_for_delivery` → `delivered` → existing `held`/complaint window → `completed`. Only an Admin may mark `handed_to_delivery`, after courier pickup is confirmed, and a required note records the courier confirmation reference/comment in delivery history/audit; sellers cannot mark handover. That atomic transition ends buyer pre-handover cancellation and stops the handover clock.
- Order failure exits: unpaid `reserved`/`payment_pending` → `cancelled` on expiry or permitted cancellation; funded pre-handover cancellation → `cancelled` plus full system refund; funded order not handed over within 72 hours → `cancelled` plus full system refund. Post-handover issues are recorded for manual resolution; no new automatic entitlement is inferred.
- For an Admin handover request, include the courier pickup timestamp entered by the Admin and the required note. Reject a timestamp in the future or before `funded_at`. Persist both the courier pickup time and the server recording time. While the order remains in the funded, pre-handover state, accept a pickup timestamp at or before `handover_deadline_at`, even if the request is recorded after that deadline but before the timeout cancellation commits. Lock and recheck against the timeout worker so exactly one transition wins. A pickup timestamp after the deadline receives `409`. If timeout cancellation and refund have already committed, receive `409`, do not reopen the order, and create one `late_handover_after_auto_cancel` manual exception visible in the Admin issue list.
- `payment_pending` → `succeeded` only from a verified gateway webhook. Browser redirects are display-only and cannot fund an order. Gateway failure updates payment attempt state but does not itself cancel a still-valid reservation unless its expiry/cancellation rule applies.
- Manual delivery status is an Admin-only transition; only authorized Admin `order.mark_delivered` may mark Delivered. Use the existing permission-based route pattern rather than role checks scattered in services.
- For the new funded flow, the Admin-only Delivered transaction creates the `payout_holds` row and begins the existing configurable hold and complaint windows required by FR-45b–FR-45h. This is the new-flow payout-hold trigger (the legacy COD path currently starts one from `cod_collections`); preserve the complaint-window behavior and FR-65 manual seller payouts.

### Temporary `Bag` compatibility

Treat legacy `bag` as a temporary compatibility alias for `reserved` only at API/read boundaries and for old data that still depends on it. New fixed-price Buy writes canonical `reserved`, never creates an offer or requires `accepted_offer_id`, and exposes `reserved` as canonical state. Remove the alias only after all stored Bag rows and consumers/tests have been migrated, checked, and the separately gated contract step confirms no dependency remains.

## 4. Concurrency and money races

- **Atomic Buy / one listing:** in one transaction, lock the listing row `FOR UPDATE`, re-read status/price/seller, reject unavailable/self-purchase, check supported city and current price, expire stale reservation state using `now()`, enforce buyer cap, insert reservation/order/payment-intent data, and enqueue durable work transactionally. The active-listing partial unique index is a second line of defense. Return conflict if another Buy wins.
- **Buyer cap under concurrent Buy:** serialize all active-unpaid count-and-insert operations for a buyer by locking the buyer row (or a transaction-scoped advisory lock keyed by buyer ID) before counting. Use the server setting (initially three), count only active unpaid reservations with `expires_at > now()`, and recheck in the transaction. Test simultaneous Buy requests for different listings by the same buyer.
- **Price revision approval:** approve and Buy both lock the same listing row. Approval checks for a non-expired active reservation after locking; when present it stays pending. Buy locks/rechecks the listing price and snapshot before creating reservation.
- **Buyer cancel versus Admin handover:** both transactions use the common lock order listing → reservation/order → payment → refund aggregate. Handover requires courier pickup confirmation and its required note before committing. Exactly one transition wins; the loser receives `409`. If funded buyer cancellation wins before handover, it creates exactly one full system refund intent in the same transaction. If Admin handover wins, buyer cancellation is no longer permitted.
- **Expiry versus payment:** worker and webhook processing serialize on the same listing/reservation/order lock path and use database time. Exactly one transaction can transition an active reservation. If payment wins while active, mark funded; if expiry/release commits first, a later successful capture is marked late and refunded via a durable idempotency key—never resurrect the reservation. Persist provider event/capture timestamps for reconciliation, but do not use a client-supplied timestamp as authority.
- **Handover deadline:** set `funded_at` from database time when funding commits and `handover_deadline_at = funded_at + INTERVAL '72 hours'`. The Admin handover request carries the Admin-entered courier pickup timestamp (not a future time and not before `funded_at`) plus the note; the server stores both that pickup timestamp and the recording timestamp. Lock and recheck against the timeout job. If timeout has not committed and the actual pickup was at or before the deadline, accept even when the record arrives after the deadline; if pickup was after the deadline, return `409`. If the order has already been auto-cancelled and refunded, return `409`, do not reopen, and create the `late_handover_after_auto_cancel` exception for manual staff resolution. This is a fixed elapsed 72-hour interval, not three calendar or business days.
- **Duplicate webhook:** unique `(provider, event_id)` inbox insert and unique provider transaction reference suppress duplicate deliveries; payment/order transition is transactional and state-checked. A duplicate returns success after the first verified event is durably recorded; it cannot duplicate ledger or refund effects.
- Establish and test one lock order for all money paths (listing → reservation/order → payment → refund aggregate) to prevent cross-path deadlocks, including buyer cancel and Admin handover. Retry only recognized serialization/deadlock conflicts under bounded policy; surface exhausted failures and dead-letter/reconcile rather than claiming success.

## 5. Server-authoritative totals

At Buy, load the current listing price and seller from the database, reject self-purchase by comparing authenticated buyer ID to listing owner, and snapshot price, configured delivery fee, total, currency, and validated delivery address. Ignore any browser-supplied fee, total, seller ID, order status, reservation expiry, or payment status. Store and calculate all monetary values as PostgreSQL `NUMERIC(12,2)` using exact decimal arithmetic.

Read delivery fee and reservation settings through the validated `platform_settings` owner; initial fee is PKR 300, reservation window 60 minutes, and active-unpaid cap three. Require recipient name, phone, supported city and sufficient address fields at Buy. Check city against active delivery coverage at Buy, not only against the buyer profile. Store an immutable order address snapshot so profile edits do not change destination.

- `verifyWebhook({ rawBody, headers, now })` → verified normalized event or explicit verification failure.

Create the hosted checkout outside the database transaction; return a checkout URL only after the adapter succeeds. If the external call fails, return an explicit service error while keeping a recoverable pending intent and active reservation; a retry uses the same key and cannot create a second charge. Define a retry/status response so the client never receives a success-shaped placeholder URL.

After verification, atomically insert the inbox event under unique provider/event ID and enqueue its processing job in that transaction; return 200 only after durable acceptance. ## 7. Refunds

**System path:** expiry, buyer pre-handover cancellation, late payment, Admin take-down of an active funded reservation, and the 72-hour seller handover timeout create a trigger-attributed full refund intent with a durable idempotency key in the same transaction as the state change. A successful capture confirmed after reservation expiry is always refunded, regardless of provider timestamp, and never reopens the reservation. A handover-timeout refund is the full amount paid: item price plus delivery fee. No second Admin approval is used. A worker calls the gateway with that key, records provider reference/status, and retries safely. A failed gateway call remains visibly pending/failed for retry and reconciliation; it never silently restores the order to a funded/active state.

**Manual path:** Admin 1 requests a permitted manual refund with a reason; Admin 2, a distinct Admin account, approves or rejects. Both must satisfy fresh TOTP step-up for their respective action using one-use, session-bound grants; reject self-approval. Apply route permissions, transactionally consume grants, lock payment/refund aggregate, write the append-only audit, and then enqueue the gateway operation idempotently. Preserve requester, approver, decision, timestamps and reason. Extend the existing step-up action model with separate refund request/approval actions; current actions do not cover refunds.

The server calculates a read-only refundable balance for each order as captured total less succeeded and in-flight refunds, with the amount split into item-price and delivery-fee components. Show it only to Admins with refund permission, in a private/no-store response; never accept a refund amount from the client. A manual request contains only the order ID in the path, a reason, and the step-up grant. The server uses the freshly calculated balance and Phase 4 manual requests cover the full refundable balance only. Partial amounts remain deferred under Q18.
Do not include refundable amounts or order data in application logs, in accordance with SEC-27.

**Return and dispute handling in Phase 4:** for an open dispute or return, staff record the return/delivery arrangement and a note on the order, then request any warranted manual refund through the two-Admin path. The record is not an automatic return decision or refund rule. In Phase 4, return/dispute handling remains manual; automated case handling is deferred to Phase 5 under Q15, and the end-to-end partial-refund workflow remains deferred under Q18.

Partial-refund support is limited to schema, status representation and validation: cumulative succeeded plus in-flight reservations cannot exceed the captured refundable amount. No buyer/Admin partial-refund workflow, UI, or promise is included; the complete workflow stays deferred under Q18/FR-71.

## 8. Worker jobs

- **Reservation expiry:** recurring scan of due active reservations using database time; claim batches with row locks/`SKIP LOCKED`; transition once, release listing availability, enqueue notification and any required refund intent transactionally. Idempotency key derives from reservation and expiry transition.
- **72-hour handover deadline:** set `funded_at` from database time at the funding transition and set `handover_deadline_at = funded_at + INTERVAL '72 hours'`; recurring scan of funded orders not handed to courier by that database-time deadline. Admin handover requires confirmed pickup and a note, and ends buyer pre-handover cancellation. Lock and recheck state/deadline; atomically cancel, record missed deadline, create a full refund of item price plus delivery fee and an audit action. Duplicate worker runs cannot repeat effects.
- **Gateway reconciliation (FR-70):** recurring provider report/fetch comparison against captured payment/refund records and ledger; record mismatches and alert/admin-visible work. Reconciliation identifies and reports differences; it does not automate seller payouts.
- Register jobs explicitly with the existing PostgreSQL PgBoss worker/scheduler. Choose cadence and batch size at implementation/operations planning; do not mistake scheduler enablement for an existing scheduled job. Use transactionally enqueued, deterministic job IDs and bounded retries. On exhausted retry, retain failure in dead-letter/health reporting and expose the mismatch for operator action; never silently mark money settled.
